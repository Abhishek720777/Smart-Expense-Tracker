# AI Collaboration Notes

## 1. Which Parts Were AI-Generated vs. Written by Me

### AI-Generated (scaffolding & structure)
- The initial Spring Boot project was bootstrapped using the Spring Initializr API via the AI assistant.
- The skeleton of the `Expense` model, `ExpenseRepository` interface, `InMemoryExpenseRepository`, `ExpenseService`, and `ExpenseController` were initially generated by the AI based on the assignment requirements.
- The initial test file structures for `ExpenseServiceTest` and `ExpenseControllerTest` were AI-generated.

### Written / Heavily Modified by Me
- **`Expense.java`**: The AI initially used Lombok (`@Data`, `@Builder`) for the model. After discovering Lombok caused a fatal JVM crash (`ExceptionInInitializerError: com.sun.tools.javac.code.TypeTag :: UNKNOWN`) on our Java 25 environment, I removed it entirely and hand-wrote a full builder pattern, getters, setters, and constructors — a deliberate architectural choice, not just a fix.
- **`pom.xml`**: Significantly reworked multiple times. The AI's initial Initializr output used invalid artifact IDs (`spring-boot-starter-webmvc` instead of `spring-boot-starter-web`) and Spring Boot `4.1.0-SNAPSHOT`. I identified and resolved a chain of Java 25 compatibility issues: upgrading to Spring Boot 3.4.3, pinning `maven-compiler-plugin` to `3.14.0`, setting bytecode `<release>21</release>` (so Spring's ASM 9.7 could read class files), and adding JVM flags for Mockito/Byte Buddy.
- **`InMemoryExpenseRepository.java`**: The AI initially suggested a simple `HashMap`. I changed this to `ConcurrentHashMap` to ensure thread-safety under concurrent HTTP requests.
- **Validation logic**: I verified that `@DecimalMin(value = "0.01")` was used instead of `@Positive` — the difference matters because `@Positive` allows `0`, while our API should reject zero-amount expenses.

## 2. What I Validated, Tested, or Changed — and Why

- **Removed Lombok entirely**: Confirmed Lombok's annotation processor caused a fatal crash with Java 25 (`sun.misc.Unsafe::objectFieldOffset` is removed). Rather than downgrading the JDK, I chose to write explicit code — it's more readable and has zero runtime dependencies.
- **Java 25 compatibility chain**: Systematically diagnosed and fixed a 5-step dependency chain:
  1. Wrong test dependencies → replaced with `spring-boot-starter-test`
  2. `maven-compiler-plugin 3.13.0` crashes on Java 25 → upgraded to `3.14.0`
  3. Spring Boot 3.3.x ASM 9.6 can't read Java 25 class files → upgraded to Spring Boot `3.4.3`
  4. Byte Buddy (Mockito) doesn't support Java 25 by default → added `-Dnet.bytebuddy.experimental=true`
  5. Spring Framework ASM 9.7 supports up to Java 24 bytecode → set `<release>21</release>` as compile target
- **Validated all 7 tests pass**: `ExpenseControllerTest` (3 tests via MockMvc), `ExpenseServiceTest` (3 tests via Mockito), `SmartExpenseTrackerApplicationTests` (1 context load test).
- **Validated input rejection**: The `addExpense_InvalidInput_ReturnsBadRequest` test specifically verifies that blank title and negative amounts are rejected with HTTP 400.

## 3. AI Suggestions I Decided Not to Use — and Why

- **Lombok**: The AI suggested Lombok for cleaner model code. I rejected this after it caused a JVM-level crash on Java 25 — not worth the dependency risk in a submission environment where the reviewer's JDK version is unknown.
- **JSON file storage**: The AI offered a JSON-file-based persistence option using Jackson's `ObjectMapper`. I decided against it because: (a) the assignment explicitly says no DB is required, (b) file I/O introduces cross-platform path risks, and (c) file-based concurrency is more complex than a `ConcurrentHashMap`.
- **Database (H2/PostgreSQL)**: The AI offered to configure an in-memory H2 database. I declined — in-memory Java collections are lighter, simpler, and fully sufficient for the scope of this assignment.
- **Docker support**: The AI offered to generate a `Dockerfile`. I chose OpenAPI/Swagger docs as the bonus instead, as it provides immediate value to anyone reviewing the API and requires zero additional tooling to use.
